Zest architecture

A minimal, fast Finder replacement for macOS. Three artifacts cooperate through a single shared file: the columnar index on disk.

The three artifacts

Zig · CLI / daemon
zest-indexer
src/indexer_main.zig

Walks the filesystem, writes the index, watches for changes. Default mode does an initial full scan then loops on FSEvents with a 30 s / 1000-event coalesce and a 24 h full rescan.

Zig · static lib
libzest-core.a
src/zest_core_lib.zig · C ABI

Pure-CPU search engine. No main, no Io handle — it borrows caller-provided bytes (a Swift mmap) for the lifetime of the Core. Fourteen exported functions expose queries, cancellation, sidebar aggregates, and query-compatible case folding.

Swift · GUI
Zest.app
Sources/Zest/... · AppKit

Native AppKit window. Links libzest-core.a via Package.swift. ZestCore mmaps the index once and wraps the C ABI. The UI never iterates an index — it asks, gets back a borrowed Row, copies the strings, formats.

What lives where

Zig — the engine

All "is this a PDF / named report / large" decisions. The index format, the bulk scanner, the FSEvents watcher, the SIMD substring search, the bitmap intersection, the cat:/ext:/kind: parser, the per-folder color/pin/filter stores, the daemon process management, the launchd plist generator.

No UI, no networking, no global state. The static library has no main and no Io handle, which makes it trivial to embed.

Swift — the shell

Window chrome, AppKit wiring, keyboard shortcuts, the table view, the sidebar tree, context menus, the "Open in Finder" / "Open in Terminal" calls, the pin/filter config persistence, the dark Darcula theme.

Nothing search-shaped lives in Swift. A single ZestCore owns the mmap and the Core handle; every other component goes through it via AppCoordinator.

Index file format — index.zst, ~80–200 MB on a 5 M-file home, custom binary

┌────────────────────── HEADER (80 bytes) ──────────────────────┐
│ magic  │ version │ padding │ 8 × u64 fields / section offsets  │
│"ZESTIN"│   u32   │   u32   │ entries · created_at · 6 offsets  │
├──────────────────── NAMES column ─────────────────────────────┤
│ u32 offsets[num]  ·  u16 lengths[num]                           │
│ u32 blob_len  ·  original blob   ·  u32 lower_len  ·  lower blob│
├──────────────────── PATHS column ─────────────────────────────┤
│ u32 parent_id[num]    ← 4-byte index into the dir table        │
│ u32 dir_count                                                   │
│ u32 dir_offsets[dir_count]  ·  u32 dir_blob_len  ·  dir_blob   │
├──────────────────── METADATA column ──────────────────────────┤
│ u64 size[num]  ·  i64 mtime[num]  ·  u8 kind[num]  ·  u8 cat[num]│
├──────────────────── BITMAPS ───────────────────────────────────┤
│ u32 num_bitmaps                                                 │
│ for each: u8 cat · u32 count · u32 indices[count]   (sorted)   │
├──────────────────── HISTOGRAM ─────────────────────────────────┤
│ u32 counts[dir_count][category_count]                            │
├──────────────────── EXTENSION BREAKDOWN ───────────────────────┤
│ per directory × category: top extension names and u32 counts    │
└──────────────────────────────────────────────────────────────┘

Why columnar. The folded-name blob is one contiguous []u8 that SIMD substring search can scan in a single pass — the row index is recovered by binary search through the u32 offsets array. Folding is length-preserving, so offsets also address the original UTF-8 blob. The v7 reader accepts layout-compatible v6 indexes and uses their ASCII query fold until the daemon publishes a v7 rebuild. The u8 kind / u8 category arrays plus the per-category sorted u32 index lists let the search engine eliminate rows that don't match a cat:code / ext:pdf filter in O(1) per candidate. Directory paths are stored once in a deduped table; each entry holds just a 4-byte parent_id.

ZestRow is a fixed-layout extern struct that Swift consumes through a Clang-imported zest_core.h — the layout cannot drift. Strings borrow into the mmap; Swift copies them to String immediately on receipt. The query string is parsed with filters.parse inside zest_query, so "cat:code" reaches the bitmap path and not the text path. Swift uses zest_casefold_utf8 to keep structured extension filters in the engine's canonical form.

One search, end-to-end

┌──────────────────┐
│ macOS filesystem │  ~/  (kernel)
└────────┬─────────┘
         │ getattrlistbulk(2)  ·  8 worker threads
         ▼
┌──────────────────┐
│ bulk_scan.zig    │  per-worker .scan.tmp.N  (TSV)
└────────┬─────────┘
         │ read back, build columnar
         ▼
┌──────────────────┐
│ builder.zig      │
│   → .tmp file    │  atomic rename(2)
└────────┬─────────┘
         │
         ▼
┌──────────────────────────────────────┐
│ ~/Library/Application Support/zest/  │
│           index.zst                  │ ◀── mmap()'d by Swift at startup
│                                      │     (PROT_READ, MAP_PRIVATE)
└────────────────┬─────────────────────┘
                 │
                 ▼
        ┌──────────────────┐        ┌──────────────────────┐
        │ libzest-core.a   │ ◀─ FFI │ Zest.app  (Swift)    │
        │   zest_query(…)  │        │  NSTableView + UI    │
        │   IndexReader    │        │  + AppCoordinator    │
        │   search()       │        │  + ZestCore          │
        └────────┬─────────┘        └──────────┬───────────┘
                 │                              │
                 │ [SearchResult]{name,         │ FileItem  (copied
                 │  dir_path,size,mtime,        │ strings, formatted
                 │  kind,category}              │ size, kind color)
                 │  — borrows mmap              │
                 ▼                              ▼
           raw bytes  ───────────────────►  rendered row

The daemon never talks to the GUI. The GUI never talks to the daemon. They cooperate only by reading and writing the same file. Atomic rename + a fresh inode is the entire synchronization mechanism.

One rebuild, in five steps

  1. Bulk scan — 8 worker threads, each pulling directories off a shared queue, calling getattrlistbulk in batches, streaming TSV lines into their own .scan.tmp.N file under ~/Library/Application Support/zest/.
  2. Build — reads the TSV files back (any order), deduplicates paths into a directory table, accumulates per-category sorted index lists, writes the columnar layout into one contiguous []u8.
  3. Atomic write — writes to index.zst.tmp then rename(2)s to index.zst. The inode changes; any process holding a stale mmap keeps its snapshot until it reopens.
  4. Mtime / stat — the file's mtime + size are sufficient for any client to decide "the index changed, re-mmap" without parsing the bytes.
  5. Cold reload — on next launch the Swift app's ZestCore.init mmaps the fresh file. (The old Zig UI polled every 5 s; see "open questions" below.)

Threading model

ComponentThreadsNotes
Indexer daemon 1 + 8 1 process · 1 main thread (FSEvents + CFRunLoop) · 8 scan workers (max_scan_threads = 8, measured sweet spot on 12-core).
Search engine sync, cancellable searchCancellable accepts an optional atomic u32 cancel flag. Text scans poll it every 64 KiB of candidate positions, filter-only scans every 512 entries, and cancellation returns error.SearchCancelled. Swift creates one token per query and cancels the previous token before enqueueing its replacement.
Swift UI main + 1 Main thread drives AppKit. The sidebar histogram kicks one userInitiated DispatchQueue.global task to recompute category counts and hops back to main to rebuild rows.

Open questions / known gaps

  • No Swift-side reload on rebuild. The Swift ZestCore.init mmaps the file once. A rebuild by the daemon is invisible until the app restarts. The old Zig UI polled the inode every 5 s (App.checkForIndexUpdate, app.zig:236); the Swift app should adopt the same pattern.
  • No "scanning" state. If index.zst doesn't exist, the Swift app silently returns no rows. A startup-time stat + empty-state message ("no index — run just index") would help.
  • Unbundled app. main.swift calls NSApplication.shared + setActivationPolicy(.regular). It works but has no real Info.plist or app bundle, so Finder metadata and file-association handling are minimal.
